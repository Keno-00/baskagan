# AI and agent workflows

This guide follows the path from project understanding to an agent run and then to change review. First, SDE builds a source-backed model of the project. When you chat about one part, SDE supplies focused context for that conversation. If an agent proposes a change, review the diff and its source baselines before saving it. For opening a project and navigating its concepts, see the [user guide](USER_GUIDE.md).

## Project understanding

To build the project model, set **Settings → Model → Default Small Model** first. SDE then asks that model to explain the project in the background; this work is separate from chat. The model returns concepts, source references, and typed workflow connections. SDE checks each path, source type, hierarchy, symbol, and inclusive line range. If a check fails, the model can correct its output up to three times. Only validated output is saved to `.dado/systems.json`, so a failed update leaves the last good model in place. Later source changes start a refresh. If no small model is configured, generation waits until one is selected.

After the model is ready, select a concept to keep its explanation and source references visible. Explore from project purpose, then move through responsibilities to implementation. When a source link is selected, SDE opens its file or exact range in the right editor. The selected concept also sets the chat context: chat receives that concept's explanation, its place in the hierarchy, its relationships, references, and notes. A source range is included only while its recorded revision still matches. Other files are not loaded into chat automatically; inspection tools can read them when needed. Ideas and annotations keep their stable concept identity in the project state.

## Chat, tools, and run lifecycle

Before sending a message to Codex, connect the installed Codex App Server in Model Settings and sign in. Set `DADO_CODEX_BIN` if SDE should use a particular executable. Then choose a model from the runtime's model catalog. Sending a message sends its supplied context; selecting an attachment alone does not send it. In Chat mode, the model uses the supplied context only. In Inspect mode, it can also list project entries, search literal text, and read files. Open editor snapshots are captured when you send the message, and tool rows show what the model did. Folder references list their immediate entries; they do not preload all files below them. Agent modes appear after the Codex runtime initializes. Skills and Boost are still under development. Credentials stay outside the project.

Each run belongs to the open project. If another conversation starts work while a run is active, that work waits in a queue and can be stopped before it begins. Closing or switching projects stops the backend process tree owned by that project. SDE saves project identity and run metadata under `.dado/project.json` and `.dado/runs/`. If the app restarts or disconnects before work is resolved, SDE marks it interrupted and does not replay it automatically. Hiding a panel does not stop its run.

## Permissions and change review

In Inspect mode, an agent can propose edits to existing text files and, on Windows, additions of new text files. It makes these proposals in an isolated snapshot under `.dado/workspaces/`. To review one, open the change icon on the reply; it shows a diff. Choose **Apply to editor** only after reviewing it. SDE checks the editor and disk versions first, preserves captured unsaved content, and leaves the result unsaved so you can inspect it before saving. If the file changed outside the review, SDE blocks the apply instead of overwriting your text. Approved commands can also produce additions and deletions; review marks each operation and checks for conflicts. On Windows, Apply opens additions as unsaved editor tabs and marks deletions as read-only pending deletions. Save commits the reviewed operation. Binary changes are not included in this text review flow.

Choose a permission mode from the selector beside the plus button before you send a message: **Chat**, **Inspect**, **On approval**, or **Full access**. Full access is marked with an orange hazard icon. It lets native Codex tools create files, edit files, and run commands in the live project without an approval step. Because those changes happen live, Full access does not use proposal-only tools or **Apply to editor**. When a run ends, clean editor tabs refresh and unsaved buffers stay as they are. A permission change applies to the next run; an active run keeps the permissions it started with.

When a command needs approval, SDE shows the exact command and its reason. Choose **Run once** to allow that one pending command, or **Decline** to stop it. The grant is tied to that command, run, and project generation. It expires after five minutes and cannot be reused after a stop, project switch, or restart. An approved command runs in the project's working copy with your operating-system permissions. It has a 1–120 second timeout and a 64 KB output limit for each stream. This working copy is **not an operating-system sandbox**.

After the command runs, text edits, additions, and deletions become proposals for review. Binary, oversized, or excess changes stay in the working copy and are listed in the review notes. On Windows, additions and deletions can be staged in editors and committed with Save. SDE treats a missing file differently from an empty file; if another process creates or edits a file at the same time, the reviewed change is blocked. Dependency, generated, and private files are excluded from the working copy, so checks that need those files may require Full access. Expandable chat rows show native command and file-edit activity. A finished activity cannot restart from a repeated terminal event. Failed exits, unconfirmed outcomes, and interrupted work remain distinct; interrupted work is never shown as successful.

For each run, SDE also records where its context came from: resource identities, hashes, sources, line ranges, and reasons for inclusion. Captured editor buffers remain separate from the files on disk. Root and applicable nested `AGENTS.md` instructions are supplied with their revisions, but they cannot grant more tool permissions. The provenance manifest stores this metadata; it does not copy file contents.

## Skills

To use a skill, enter `/skills` and choose one from the runtime or private project skills. The picker adds it to the next message; pressing Enter selects it without sending the message. When you send, SDE captures the skill instructions and supporting files, checks that their revisions have not changed, and records their provenance. A skill cannot grant tool permissions.

The selected permission mode determines how the skill can be used. Chat receives the skill instructions only. Inspect and On approval can list and read captured supporting files through scoped, read-only tools. Full access uses native tools. SDE records the captured hashes of files it reads. The picker also checks dependencies and invocation rules in `agents/openai.yaml`; a skill that needs an external tool stays disabled until that tool is integrated. Changing this configuration invalidates an earlier selection. Snapshot lifecycle handling and additional integration checks are still in development.

To make a skill, enter `/create-skill` and provide its name, purpose, activation conditions, and scope. The selected model drafts instructions only; it does not add execution tools. SDE validates the draft and opens it in the editor. Review or edit it there. Then open Create skill again and choose **Publish** beside the draft. Before publishing, SDE checks for outside edits and will not overwrite an existing skill. Private skills are saved in `.dado/skills`; shared skills are saved in `.agents/skills`.

If you close the app before publishing, the draft remains in `.dado/skill-drafts`, but it is not available to skill discovery. Creating a skill also keeps the current message draft and pending attachments or comments. After a private skill is published, its Share icon copies the skill and supporting files to `.agents/skills` while keeping the private copy. Sharing stops if the revision is stale or a shared skill with the same name already exists.
